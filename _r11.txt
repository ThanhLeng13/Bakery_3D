fix: collect enough image-search results, and stop reporting a fake accuracy

Seven review findings. Six were valid and are fixed; the seventh turned out to be
the most serious thing in this branch, and it invalidates a number I reported
earlier.

The accuracy figure first. I reported "top-1 100%" for the new catalogue. That
was wrong, and wrong in a way worth spelling out because it looked like a result.
Every product in the catalogue has exactly one image - 117 of 119 - and the old
evaluation took sims[0] for a product whose only embedding was the query image
itself. So it compared each photo to itself and scored ~1.0. The number was
guaranteed by the method, not produced by it. Fixed by excluding the query image
by image_url rather than by position; the script now finds nothing left to
compare and refuses to print a number, which is the honest outcome. A real
hold-out needs two images per product, so the report now says that plainly
instead of quoting a figure that cannot be reproduced.

The retrieval bug is real and was intermittent, which is worse. match_cakes ranks
the whole catalogue and takes no filter argument, so filtering happens in Python.
Fetching match_count * 10 capped at 60 assumed the wanted group is spread evenly
through the ranking; measured on the live catalogue, asking for 10 rows returned
only 3 cakes because sweet items ranked above them. A customer asking for 6
birthday cakes could silently receive 3. It now pages until it has match_count
matching rows or the RPC runs out, with a scan ceiling so a large catalogue cannot
loop forever. Unfiltered queries still make exactly one RPC call.

Also: import_cake_images used hash() for the storage object path, which is salted
per process - three runs produced three different paths, so every rerun duplicated
uploads instead of being idempotent. Now a sha1 of the relative path, verified
stable across processes, and an already-existing object is reused rather than
counted as a failure (confirmed against live Storage, which answers 409
"already exists"). build_names_review assigns names by position, so adding one
photo would shift every later name onto the wrong cake; it now refuses to run when
the file count and name count disagree and lists what is missing. apply_names
demanded credentials before the --dry-run branch, making preview useless without a
configured .env; the check moved to just before create_client. Three evaluation
scripts divided by a possibly-empty collection, and price_cakes called min() on an
empty list.

One finding I did not act on as written: the reviewer suggested keeping sims[0]
when only one embedding remains after exclusion. That is the bug, not the fix -
it restores the self-comparison. Products left with no alternative image are
skipped and counted instead.

Backend 248 tests pass, including three new ones covering the paging path; I
checked they fail against the old logic rather than assuming they would. tsc and
lint clean, live endpoint returns the requested count for all three filter modes.
